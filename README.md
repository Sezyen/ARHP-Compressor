# MienArch ARHP Compressor 技术说明文档

**版本 1.1.0.2 ｜ 许可协议：GPL-3.0-or-later**

---

## 1. 项目概述

MienArch ARHP（下文简称"本工具"）是一款面向长期数据归档与容错存储场景的开源压缩归档程序。其设计目标是在单一格式内集成四项在常规归档软件中彼此割裂的能力：

1. **高压缩比数据缩减**：基于 zstd 压缩器（压缩级别 0–22，0 级为纯存储模式）；
2. **机密性保障**：基于 AES-256-GCM 的分块认证加密，密钥派生可选 PBKDF2-HMAC-SHA256 或 Argon2id；
3. **比特级容错恢复**：基于 GF(2⁸) 域上 Reed-Solomon 纠删码的内嵌恢复数据，可自动修复归档中随机发生的块损坏；
4. **归档头元数据保护**：自 v1.1.0.0 起，归档头本身亦纳入 Reed-Solomon 保护，并以自描述尾注（trailer）结构提供自定位能力。

本工具同时提供 `.arhp` 原生格式与 `.zip`、`.7z` 两种主流格式的读写支持，并配有命令行与图形界面（PySide6）两套交互方式。

## 2. 系统架构

代码库采用双文件模块化结构：

| 文件 | 职责 |
|---|---|
| `arhp_core.py` | 核心库：Reed-Solomon 编解码、zstd 流式封装、认证加密、归档格式（v3）、分卷管理、CLI 入口 |
| `arhp_main-1.1.0.2.py` | 主程序入口与 PySide6 图形界面，自动加载同目录核心库 |

### 2.1 归档文件布局（v3 格式，大端字节序）

```
magic      6B   b"ARHP\x00\x01"
hlen       8B   uint64，头长度
header     JSON（分块表、CRC32 校验值、加密参数等）
data       N 个分块（按真实长度连续存放；zstd 流或加密密文）
parity     K 个 Reed-Solomon 校验块（等长 block_size）
hblocks    HB 个头分块（头 JSON 按 64 KiB 等长分块，末块零填充）
hparity    HP 个头校验块
trailer    JSON + CRC32(JSON) + 长度 + 魔数（位于文件最末尾，支持自尾向前定位）
```

v3 格式的关键设计在于：即使头 JSON 损坏，读取端仍可依据尾注中记载的分块布局与逐块 CRC32 对头分块执行 Reed-Solomon 恢复，仅在损坏超出可恢复上限时才判定归档不可读。

### 2.2 流式内存模型（v1.1.0.2）

旧版本实现中存在一个结构性缺陷：分块校验与纠删码编解码将全部分块一次性载入内存，导致峰值内存占用与归档大小成正比（例如 10 GiB 归档对应超过 10 GiB 的峰值驻留集）。v1.1.0.2 对此进行了重构：

- 分块校验、Reed-Solomon 编码与解码均按块 / 按列切片（column-slice）方式流式执行；
- 峰值内存由 `mem_limit` 参数显式约束（16 MiB–1024 MiB，默认 128 MiB）；
- 当工作集超出内存限制时，纠删码运算退化为多遍列切片累计模式（single-pass 内存不变，代价为数据重复读入）；
- 经 Reed-Solomon 恢复的块必须逐块通过 CRC32 复核后，方可视为有效数据进入后续解包流程。

需要指出的是，`.arhp` 格式的 tar 载荷不存在中心目录结构，故 `list` / `test` / `extract` 操作均需完整遍历载荷流（加密归档还包括解密运算）。这一成本是当前格式的固有属性，而非实现层面的可优化项；`info` 操作不受影响。

## 3. 密码学与容错语义

### 3.1 加密子系统

- **载荷加密**：分块 AES-256-GCM，每 4 MiB 明文为一独立认证加密单元；nonce 构成为 8 字节随机前缀加 4 字节大端块序号，长度恒定 12 字节；
- **密钥派生**：
  - `gcm`（默认）：PBKDF2-HMAC-SHA256，60 万次迭代，向后兼容全部旧版本；
  - `argon2id`：Argon2id 内存硬派生（默认 3 轮 × 128 MiB × 4 线程），显著抬高 GPU/ASIC 离线穷举的成本；
- **头认证**（v1.1.0.2 新增）：加密归档的头 JSON 纳入 HMAC-SHA256 认证（`header_mac` 字段），头数据（分块表、加密参数等）遭篡改时将得到明确报错，而非依赖可伪造的 CRC32 + Reed-Solomon 组合兜底。

### 3.2 安全语义澄清

须特别说明：CRC32 与 Reed-Solomon 均属线性码，其纠错能力仅针对**随机发生的比特损坏**；二者均无法抵御**恶意篡改**——攻击者可在重算 CRC 的前提下伪造校验块。因此：

- **未加密归档**：仅具备抗随机损坏的容错能力，不具备防篡改能力；
- **加密归档**：载荷本就逐块经 GCM 认证，加之头 HMAC 认证，具备完整的篡改检测能力；由于 Reed-Solomon 恢复出的块经 CRC32 验证后与原始密文逐字节一致，加密归档的随机损坏同样可以被自动修复（先纠错、后认证）。

### 3.3 兼容性说明

- v1.1.0.2 可正常读取全部旧版归档（v1.0.2.3 的 nonce 布局、v1.1.0.0 之前的 v2 头布局均在读取侧得到兼容处理）；
- ≤1.1.0.1 版本读取 v1.1.0.2 创建的**加密**归档会因 `header_mac` 字段引入的 `header_crc` 不匹配而拒绝读取；未加密旧归档互读不受影响。

## 4. 功能要点（v1.1.0.2）

- 分块校验与 Reed-Solomon 编解码全面流式化，峰值内存可控（`--memory` / GUI 内存限制档位）；
- 加密归档头 HMAC-SHA256 防篡改认证；
- `extract_archive()` 返回值修正为解压文件数（与 zip/7z 路径行为一致）；
- 分卷数量超过 999 时的命名与定位缺陷修复（第 1000 卷起采用四位命名 `.1000`，卷名正则放宽为 `\d{3,}`）；
- `split_volumes` 中途失败时自动清理半成品分卷，原归档保持不动；
- 解压时权限掩码收紧为 `0o777`，不再原样恢复 setuid/setgid/sticky 位；
- tar 硬链接条目此前被静默跳过导致数据无声丢失，现以 `os.link` 还原（失败退化为复制内容），前向引用留待收尾重试；
- `decrypt_file` 异常处理收窄：仅 GCM 认证失败（`InvalidTag`）被映射为密码/篡改错误，其余真实故障原样抛出；
- 参数不再被静默改写：`block_size < 4096` 直接报错；分块数超出 255 上限时自动增大分块大小并通过进度消息明确告知；
- 临时目录加固：`makedirs` 后通过 `lstat` 校验最终节点为真实目录，以缩小 TOCTOU 攻击窗口。

## 5. 使用方式

### 5.1 命令行

```bash
# 创建归档（扩展名决定格式；arhp 支持 zstd 0-22 级 + Reed-Solomon 恢复数据）
arhp create -o backup.arhp -l 9 -r 3 -b 1M --encrypt 目录/

# 加密归档（可选 Argon2id 密钥派生）
arhp create -o secret.arhp -p 密码 --crypto argon2id 文件1 文件2

# 分卷输出
arhp create -o big.arhp -V 4480M 大目录/

# 解压 / 测试 / 列目录 / 信息
arhp extract archive.arhp -o 输出目录 [-p 密码] [--only 条目名...]
arhp test archive.arhp
arhp list archive.arhp
arhp info archive.arhp

# 内存限制（16M-1024M，默认 128M）
arhp extract big.arhp -m 512M
```

环境变量 `ARHP_PASSWORD` 可作为密码来源；密码亦可交互输入。

### 5.2 图形界面

```bash
python arhp_main-1.1.0.2.py        # 双击/无参数时自动进入 GUI
```

界面提供两个标签页：**添加压缩包**（打包、压缩级别、恢复数据比例、分块大小、加密算法、分卷大小）与**打开压缩包**（7-Zip Manager 风格的内容预览树、选择性解压、完整性测试、归档信息）。任务在独立工作线程中执行，主界面保持响应。

### 5.3 环境依赖

- Python ≥ 3.8
- 必需：`pyzstd`（或 `zstandard`）、`cryptography`
- 可选：`PySide6`（GUI）、`argon2-cffi`（Argon2id）、`py7zr`（.7z 格式）

```bash
pip install pyzstd cryptography PySide6 argon2-cffi py7zr
```

## 6. 已知限制

1. 纠错与容错能力以上限为界：可恢复块数不超过校验块数量（恢复数据比例越高，容错上限越高）；
2. `.arhp` 无中心目录，列目录 / 测试 / 解压须完整遍历载荷流，大体积加密归档的元数据操作成本较高；
3. 标准库 `zipfile` 不支持写入加密 zip，加密需求请改用 `.arhp` 或 `.7z`；
4. CRC32 + Reed-Solomon 不防恶意篡改；防篡改需求应使用加密归档。
